# World content repository format and source loading

`world.json` is the only mutable selection document. Version 2 (`elsemesh.world-repository/2`) selects an immutable snapshot; JSON components live at `snapshots/<snapshot SHA-256>/<role>.json`. Roles are metadata, terrain, objects, features, environment, spawn, geography and assets. Components carry exact path, SHA-256 and byte count. The snapshot hashes the ordered role/hash/byte-count records, excluding the paths. Binary content lives at `assets/<SHA-256>.glb` or `imagery/<SHA-256>.png|jpg`. Existing content is retained by folder saves. Version 3 (`elsemesh.world-repository/3`) adds a hashed `connections` JSON component whenever the project declares portals, water or retro terminals; see [authored connections](portal-world-format.md). Projects without those declarations continue to pack as version 2.

The manifest includes stable `world` metadata (`worldId`, `regionId`, name, description), `regions: [{regionId,name,scene:{snapshot}}]`, `projectSchema`, `engine`, `attribution` and optional `provenance`. The current engine supports exactly one region/scene. It rejects multiple regions rather than silently ignoring them. World/region identifiers must match the hydrated scene. Renaming or relocating a repository does not change world identity.

`engine.contract` must equal `elsemesh.worlds.runtime/1`. `engine.requires` is an explicit supported capability list: `project/2`, terrain, objects, hierarchy, features, neon-sign, computer, geography, terrain-imagery, weather, `portal/1`, `water/1` and `retro-terminal/1`. Unknown capabilities/contracts and missing requirements inferred from the scene reject the candidate. Neon and computer schemas remain their existing validated declarative forms; no script execution is introduced. `engine.commit` records source provenance (initial reference `95719848d5ffa4428b57c75c272483e1c2113a72`) and is not the compatibility predicate or evidence of original engine runtime acceptance.

`attribution` contains authors plus optional license/source. Each asset retains its own source and license. Optional provenance records sourceWorldId, sourceLocation, full sourceCommit and sourceDigest. This does not grant any new asset rights. `packWorldRepository(project, options)` accepts attribution/provenance as manifest options, without extending WorldProject. `forkWorldSource(loaded,name?)` clones authored content, generates new world/region identifiers and returns project plus packOptions preserving attribution and source provenance. Object and asset identifiers remain local to the cloned scene.

## Reader compatibility and trust boundary

Version 1 and version 2 repositories remain readable through the same validator. Opening does not write a migration. Explicit packing emits v2 for basic projects or v3 for projects with optional connection declarations. Engines that do not support v3 reject its schema rather than discard those declarations. `unpackWorldRepository(read)` preserves its legacy project return API. `inspectWorldRepository(read)` returns project, manifest and contentDigest after complete validation. Existing `packWorldRepository(project)` calls remain valid.

The reader receives only allowlisted exact relative paths. Manifests are limited to 64 KiB; repository reads and hydrated project content to 25 MiB. Repeated binary references count separately toward hydration budgets; imported GLB assets total at most 15 MiB. Hashes, byte counts, content-addressed names, snapshot digest, final project structure, embedded GLB validity and scene requirements are checked before acceptance. LFS pointers, executable hooks/scripts/extensions and arbitrary engine requirements are rejected. Unreferenced files are neither read nor executed. Content hashes prove internal consistency, not author authenticity.

## Shared source API

`loadWorldSource({kind:'local',read,label?})` and `loadWorldSource({kind:'github',owner,repository,path,ref?,commit})` feed the same validator. The resulting identity separately records worldId, source location, resolved full commit when remote, manifest contentDigest and a new sessionId. Content digest covers the manifest, whose references recursively bind component and binary contents.

`parseGitHubWorldLocation(url)` accepts credential-free HTTPS github.com repository/tree URLs. Directory path segments and refs are validated. Branches with slashes can be passed through the explicit `ref` property; tree URLs use one ref segment. `resolveGitHubWorldSource(location)` resolves a branch or tag through GitHub's public commits API, then returns a full 40-character commit source. Release tags can be supplied as refs. All content requests use raw.githubusercontent.com with that full commit. Public repositories only: no token, cookie, URL credentials or private authentication UI. HTTP redirects are rejected; request bodies are read incrementally with strict byte limits and an abort timeout (15 seconds default, at most 30 seconds per request). Network/CORS/API limits surface as load failures.

`checkWorldSourceUpdate(current)` resolves the saved moving ref and loads a separate fully validated candidate. It returns undefined for the same commit, rejects a changed world identity, and never mutates/applies the candidate. The caller must present an explicit apply decision. Pinned commit inputs remain pinned. A source session does not imply a networked multiplayer session or any automatic publishing.

Domain source and repository tests cover deterministic exports, non-destructive v1 reads, compatibility, traversal/hash/size/LFS/hook rejection, streaming bounds, redirects, timeout, source identity, update isolation and fork provenance. Native runtime qualification is a separate integration gate.
